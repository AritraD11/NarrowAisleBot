# Flowchart QA, 2 Oct 2026

What was checked before these figures were allowed into `main`, what was found, and what was not checked.

Short version: every node name, topic name, and number in the nine figures was compared with the source. Seven corrections were made. The original dense drawing turned out to be unreadable on a slide (6 pt text), so six slide-grade figures were added. Nothing was checked against the live Pi, and nothing was driven.

---

## 1. Slide readability, measured

Point size is what the smallest text becomes when the figure fills a 13.33 in wide slide.

| Figure | Canvas | Smallest text | On a slide |
|---|---|---|---|
| h1 whole system | 1560 x 1160 | 10 px | 6.2 pt |
| h2 drive paths | 1320 x 470 | 10 px | 7.3 pt |
| h3 ESP32 firmware | 1160 x 520 | 10 px | 8.3 pt |
| s1 to s6 | 1760 x 990 | 21 px | 11.5 pt |

So h1 to h3 are handouts: report appendix, poster, A3 print, or a slide the audience is not expected to read. Only s1 to s6 are meant to be shown. Titles on the slide set are 12 to 14 pt.

## 2. Automated layout check (`render_png.js`)

Runs in Chromium on the real IBM Plex fonts, on every figure, every time PNGs are built:

- every line of node text fits inside its box
- every band title fits inside its band
- no text leaves the canvas
- no edge label sits on a node or on another label
- (in `flowcharts.py`) no edge segment passes through a node rectangle

Result on the final build: clean on all nine. During the work the checker caught one real collision (an arrow running through a callout in the navigation slide), which was fixed. It cannot judge whether a diagram reads well, so each slide was also looked at by eye at full size. That found several things the checker cannot see, all fixed: band titles crossed by arrows (s1, handout), a label running into the merged-path arrow (s2), band titles wider than their bands (s5), and slam_toolbox drawn as a child of `sensors.launch.py` when `mapping_full.launch.py` starts both (s6).

## 4. Corrections made

1. `/esp32/command` label said "gains". The dashboard only sends `<S>`, `<E1>`, `<L1>`, `<L0>` (`phone_dashboard.py:3237, 3247, 3875, 3881`). Label fixed.
2. Stall rule read "PWM > 250"; the code is `>=` (`aislebot_esp32.ino:625`). Fixed.
3. The TF line from odometry_publisher implied only slam_toolbox reads it. Nav2 and the dashboard read it too. Label extended.
4. `smoother_server` and `waypoint_follower` are lifecycle-managed but not drawn. Now listed under "left out" in the page and here.
5. LiDAR rate was shown as a plain fact; it is a Pi measurement. Now says "measured".
6. s6 drew slam_toolbox under `sensors.launch.py`; `mapping_full.launch.py` starts both. Fixed.
7. Navigation slide used an abbreviated action name for the planner request; replaced with "plan".

## 5. Things the source shows that are not drawing errors

These are for you to decide on. None were changed.

- **Wheel-speed headroom.** teleop_asym clamps wheels at 6.28 rad/s, but esp32_bridge and the ESP32 limit is 5.20. At the Nav2 caps (0.12, 0.12, 0.30) a full strafe plus full turn needs about 5.36 rad/s, and at the manual caps (0.15, 0.15, 0.30) about 6.14 rad/s. Both are above 5.20. The bridge clamps each wheel on its own (`esp32_bridge.py:188-191`), it does not scale the four together, so a combined full-scale strafe plus turn would saturate one wheel and bend the commanded direction slightly. teleop_asym does scale all four together, but only above 6.28, which is too late to help. It only bites at the extreme corner of the command range. Read from code, not tested.
- **Stale comment.** `nav2_slam.launch.py` says `goal_pose_adapter` is inert until Foxglove is pointed at it. The dashboard publishes `/goal_pose_click` now, so it is live whenever Nav2 runs.
- **Bridge default.** `esp32_bridge.py` defaults `telemetry_enabled` to False; the launch file sets it True with a comment explaining why. The figures show the launch value.

## 6. Not checked

- The live Pi. Package versions, what is deployed, live parameters. `tools/verify_live_config.sh` and `tools/pi_audit.sh` cover that.
- Anything by driving. The figures say what the code does, not that the robot behaves that way.
- PowerPoint, Keynote or Google Slides rendering. The PNGs are plain images and will look the same everywhere. The SVGs name IBM Plex first and fall back to Segoe UI or Arial, so in PowerPoint the text will be in a fallback font and slightly different in width.
- Dark-theme PNGs. Everything is drawn on white.
