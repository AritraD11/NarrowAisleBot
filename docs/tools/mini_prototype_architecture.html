NarrowAisleBot · small-scale prototype · ESP32 + Raspberry Pi 5

A one-third-scale asymmetric mecanum robot for PID & SLAM.

Same Pi. Same LiDAR. Same kinematics. New 12 V motors with the encoder built in — because the full-size AisleBot's separate encoders quit. Here is the entire hardware, electronics, physics, and control architecture, with a live kinematics bench you can drive.

The short answers

everything you asked, up front

QuestionAnswer
Same Raspberry Pi for both? yes — ideal The kinematics node is already parameterized. The prototype is a robot profile (params YAML), not a code fork. Your SLAM config carries over.
Same ESP32? dedicated unit Same firmware, one #define switches constants. A second ESP32 (~$5) keeps both robots intact — but reusing the NAB's is fine (its encoders are dead).
Same LiDAR? yes Reuse the YDLIDAR X4 Pro — slam_nodom.yaml is already tuned to it. 0.12–12 m is ample for a small robot.
Motor driver? 2× Cytron MDD10A — dual 10 A, 5–30 V, PWM+DIR, 3.3 V logic. Same two-driver layout as the NAB → identical firmware pin map.
Wheel diameter? 80 mm mecanum (r=0.040 m) → ~1.10 m/s hardware, capped ~0.45 m/s for SLAM. 60 mm slower/torquier, 100 mm faster.
IMU? BNO055 — on-board fusion → calibrated yaw straight into robot_localization. I2C, 3.3 V, ~12 mA. (Upgrade: BNO085.)
Rated power? ~90 W continuous, >150 W transient. 3S Li-ion ~5 Ah (or 4S LiFePO₄), plus a 5 V / ≥6 A buck for the Pi.

Live asymmetric kinematics

drive it — same equations as the firmware

top view · forward = up · green fwd / red rev · brightness ∝ |ω|
within limits · no clamping
Inverse — body → wheels
ω_FR = (vx + vy + wz·K_outer)/r    ← outer
ω_FL = (vx − vy − wz·K_inner)/r    ← inner
ω_RR = (vx − vy + wz·K_inner)/r    ← inner
ω_RL = (vx + vy − wz·K_outer)/r    ← outer

r = 0.040   K_outer = 0.225   K_inner = 0.195
Forward — wheels → body (odometry)
vx = (r/4)(ω_FR + ω_FL + ω_RR + ω_RL)
vy = (r/4)(ω_FR − ω_FL − ω_RR + ω_RL)
wz = (r / (2·(l1+l2+2d)))·
        (ω_FR − ω_FL + ω_RR − ω_RL)

l1+l2+2d = 0.420

Distribution
Battery 3S Li-ion (11.1 V) ─┬─ 12 V MOTOR RAIL
  [switch + 15–20 A fuse]   │    ├ MDD10A #1 → FR, FL
                           │    └ MDD10A #2 → RR, RL
                           │
                           └─ 5 V / 6 A BUCK

One common ground across battery−, both drivers, buck, ESP32, Pi (via USB) and encoders — a missing ground link gives phantom motor behaviour (the NAB learned this). Runtime: 3S 5 Ah ≈ 55 Wh → ~30–40 min.

08

What's right, what to watch

the honest review

✓ Right

  • ✓Reusing Pi 5 + X4 Pro — the whole SLAM/Nav2 investment transfers cleanly.
  • ✓Built-in Hall encoders sidestep the exact failure that stopped the NAB.
  • ✓12 V native motors — no 24 V boost converter, lighter power train.
  • ✓2× MDD10A mirrors the NAB layout → same pin map, 10 A over ~5.5 A stall.
  • ✓Asymmetric IK preserved — the prototype stays scientifically faithful.

⚠ Watch

  • !Coarse 537.6 CPR — quantized low-speed velocity. Mitigate per §03.
  • !Re-measure feedforward: expect Kff ≈ 8–12 (NAB was ~40–48).
  • !Pi 5 can pull 5 A — undersized 5 V buck → brown-outs mid-SLAM.
  • !Confirm the ME-37 is happy at 3.3 V; else 5 V + level shifter.
  • !Need 2 LH + 2 RH mecanum wheels — a wrong hand breaks strafing.

✕ Don't

  • ✕Reuse the 24 V boost converter — these motors are 12 V.
  • ✕Drive them with a TB6612FNG (1.2 A) — it won't survive stall.
  • ✕Let MOTOR_DIR_SIGN ≠ ENC_DIR_SIGN per motor → runaway.
  • ✕Skip the fuse or the latching E-stop.
